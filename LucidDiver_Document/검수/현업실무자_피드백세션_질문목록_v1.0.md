## 1. 기획서 검수 / 포트폴리오 수준

- 현재 게임기획서를 현업 기준으로 봤을 때, 가장 먼저 보완해야 할 부분은 무엇인가요?
- 이 프로젝트가 포트폴리오로 인정받으려면 최소한 어떤 결과물이 필요할까요?
  - *예: 플레이 가능한 빌드, 플레이 영상, 기획서, 시스템 명세서, 일정표, QA 문서, 데이터표, 발표자료 등*
- 현업에서는 게임기획서를 검토할 때 어떤 기준이나 체크리스트로 평가하나요?
- 현재 기획서에서 콘셉트, 핵심 루프, 시스템 명세, UI 흐름, 일정, QA 기준 중 어느 부분이 가장 부족해 보이나요?
- 실무 기준의 게임기획서 샘플, 기능 명세서 샘플, 기획서 리뷰 체크리스트 같은 자료를 받아볼 수 있을까요?

## 2. 현재 마감 기준 우선순위 / 스코프 조정

- 현재 마감 일정 기준으로, 저희 팀이 가장 우선순위로 처리해야 할 작업은 무엇인가요?
- 지금 P0 범위에서 반드시 완성해야 하는 기능과, 과감히 잘라내거나 더미 처리해도 되는 기능은 무엇인가요?
- 일정이 밀릴 경우 현업에서는 기능을 삭제, 보류, 더미 처리, 하드코딩 중 어떤 기준으로 판단하나요?
- 발표용 빌드 기준으로 "최소 완성"의 커트라인은 어디까지라고 보시나요?
- 현재 P0 범위에서 가장 먼저 터질 가능성이 높은 병목 지점은 어디라고 보시나요?

## 3. PM / 일정관리 / 팀원 작업 관리

- 현업에서는 프로젝트 일정을 어떤 단위로 쪼개서 관리하나요?
  - *예: 마일스톤, 기능 단위, 일 단위 작업, 담당자별 태스크 등*
- 일정표에는 완료 기준을 어느 정도까지 구체적으로 적어야 하나요?
- 기획, 개발, 리소스, QA, 발표 준비가 섞여 있을 때 현업에서는 일정표를 어떻게 분리해서 관리하나요?
- 팀원별 작업 현황, 지연 상황, 리스크는 어떤 양식으로 관리하나요?
- 현업 PM 일정관리표, 업무 티켓 양식, 주간 보고 양식, 리스크 관리표 예시를 받을 수 있을까요?

## 4. 시스템 명세 / 개발 중 변경 대응

- 시스템 명세에 없던 기능이나 예외 상황이 개발 중 추가될 경우, 현업에서는 어떻게 관리하나요?
- 명세 변경이 생겼을 때 기획서, 시스템 명세서, 개발 태스크, QA 체크리스트 중 어디까지 동시에 수정해야 하나요?
- 기능 구현 중 기획자와 개발자 간 커뮤니케이션은 어떤 방식으로 하는 것이 가장 안전한가요?
- 개발자에게 전달하는 시스템 명세서에는 어떤 항목이 반드시 들어가야 하나요?
- 현업에서 쓰는 시스템 명세서, 기능 정의서, 변경 이력 관리표 예시를 받아볼 수 있을까요?

## 5. 개발 구조 / 책임 분리 / 병합 방식

- 씬 전환, 게임 상태, UI, 결과 정산, 데이터 저장 같은 구조는 현업에서 보통 어떤 매니저 구조로 분리하나요?
- GameManager, UIManager, ResultManager, DataManager처럼 책임을 나눌 때, 어디까지 분리하는 게 적절하고 어디부터 과한 구조인가요?
- 파트를 분담해 병렬 개발한 뒤 병합하는 방식에서, 병합 후 조정은 메인 개발자가 함께 담당하는 게 좋은가요, 아니면 별도 전담자가 있는 게 좋은가요?
- 6~7주짜리 프로토타입 개발에서 MVP, Assembly Definition, 계층형 구조 같은 아키텍처를 적용하는 장단점은 무엇인가요?
- 프로토타입 단계에서 구조적 안정성과 빠른 구현 속도 중 어디에 더 무게를 두는 게 좋나요?

## 6. P0 핵심 루프 / 서브컬처 상호작용

- P0에서 캐릭터 1명과의 서브컬처식 상호작용을 보여주려면 최소한 어떤 요소가 필요하다고 보시나요?
- 현재 구조는 "세션 전리품 획득 → 탈출 성공 → 기억 파편 자동 사용 → 동조율 상승 → 기록 해금"인데, 이 정도로 캐릭터 애착 루프가 전달될까요?
- 익스트랙션 루프와 캐릭터 애착 보상이 연결되어 보이려면, 발표 시연에서 반드시 보여줘야 하는 장면은 무엇인가요?
- 파밍 아이템이 단순 재화가 아니라 캐릭터 관계/기억 보상으로 이어진다는 기획 의도를 더 잘 전달하려면 어떤 보강이 필요할까요?
- 정식 출시 목적의 프로젝트라면 캐릭터 관계 보상, 파밍 빈도, 적 등장 빈도, 세션 길이는 어떤 절차로 조정하나요?
