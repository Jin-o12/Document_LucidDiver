#### 1. 초기 목표

프로젝트의 초기 목표는 완성형 게임 전체를 제작하는 것이 아니라, **PvE 익스트랙션 루프와 서브컬처 캐릭터 애착 루프가 하나의 플레이 사이클에서 실제로 결합될 수 있는지 검증하는 버티컬 슬라이스 프로토타입**을 완성하는 것이었다.

핵심 검증 루프는 다음과 같았다.

- 인게임에서 적과 전투하고 기억 파편 및 소비 아이템을 획득한다.
- 전화부스를 통해 탈출에 성공하면 기억 파편은 자동으로 사용되어 동조율 상승과 개인 심상 기록 해금으로 이어진다.
- 일반 회수품은 창고에 저장되고 다음 출격의 소지품으로 장착된다.
- 실패 시 세션에서 획득한 아이템을 잃게 하여 익스트랙션 장르의 긴장감을 전달한다.
- 로비, 출격 준비, 인게임, 결과창, 다이버 기록, 창고가 하나의 끊기지 않는 흐름으로 연결되도록 한다.

개인적으로는 PD 역할에 맞춰 세계관과 시나리오의 정합성을 관리하고, 외부 에셋을 선별하여 실제 레벨에 적용하며, 최종 빌드의 공간적·시각적 완성도를 높이는 것을 목표로 했다.

#### 2. 최종 결과물

최종적으로 다음 요소를 포함한 PC용 Unity 프로토타입과 발표용 시연 자료를 제작했다.

- 인트로 및 튜토리얼 흐름
- 로비, 출격 준비, 다이버 기록, 창고/인벤토리 UI
- 2.5D 탑다운 방식의 마트형 인게임 레벨
- 이동, 달리기, 대시, 조준, 공격, 파밍, 탈출의 기본 조작
- 적 추적 및 공격, 아이템 획득, 성공/실패 정산 흐름
- 기억 파편을 이용한 동조율 및 심상 기록 보상 구조
- 창고와 인벤토리, 퀵슬롯을 연결하는 아이템 관리 구조
- Flat Kit 기반 툰 셰이딩, 손전등과 환경 조명, 벽 투명화, 캐릭터 그림자 등 시인성 개선 기능
- 인트로·로비·튜토리얼·기초 조작을 포함한 발표용 시연 영상

- 외부 에셋을 그대로 배치하는 수준을 넘어 콜라이더, 셰이더, 조명, 카메라 가림, 렌더링 호환성을 검증하고 프로젝트에 맞게 보정했다.
- 플레이어가 어두운 맵에서도 캐릭터와 상호작용 대상을 놓치지 않도록 시인성 문제를 반복적으로 개선했다.
- 프로젝트 후반에는 발표자료 검수, 시연 영상 촬영, 발표대본 작성까지 담당하여 결과물의 전달 완성도에 기여했다.

#### 1. 협업 방식 (스크럼 주기, 사용한 도구, 회의 운영 방식)

- **스크럼:** 매일 오전 10시에 진행 상황, 당일 목표, 이슈와 블로커를 짧게 공유했다.
- **스프린트 운영:** 기획 확정 → 코어 루프 구현 → 이미지/에셋 적용 → P0.5 및 QA → 발표 준비 순서로 주차별 목표를 나누었다.
- **문서 관리:** Notion을 중심으로 기획서, 일정표, 일일 개발일지, 회고 및 발표 자료를 관리했다.
- **버전 관리:** Git/GitHub 브랜치를 활용하여 기능별 작업과 통합을 진행했다.
- **업무 공유 원칙:** 문제가 발생하면 개인이 장시간 보유하지 않고 전체 채널에 공유하며, 기획 변경은 P0 정의서와 시스템 명세서를 기준으로 판단했다.
- **리뷰 방식:** PD·PM·CP·CD·TD가 각자의 전문 영역을 담당하되, UI·기획·개발·연출 사이의 의존성이 높은 항목은 서로 검수하며 진행했다.

#### 2. 잘 진행된 점

- 프로젝트 초기에 P0 정의서와 구현 범위를 명시하여 “이번 빌드에서 무엇을 검증할 것인가”를 팀이 공유할 수 있었다.
- 매일 작성한 개발일지를 통해 진행 상황과 문제 해결 과정을 누적했고, 후반 발표 준비와 회고 작성에도 그대로 활용할 수 있었다.
- 문제가 발생했을 때 역할 경계를 이유로 미루기보다, 필요한 팀원이 구현·테스트·기획 보완에 함께 참여했다.
- 기능 구현 이후 비주얼 리소스 적용, QA, 발표 준비를 단계적으로 분리하여 최종 결과물을 정리할 시간을 확보했다.
- 주말 버퍼와 기능 동결 시점을 일정에 포함해 과도한 막판 기능 추가를 통제하려고 한 점이 좋았다.

#### 3. 개선이 필요했던 점

- P0, P0.5, 베타 단계에서 기능 범위가 점차 확장되면서 일부 문서와 실제 구현 상태 사이에 차이가 발생했다.
- 후반부에 렌더링, 셰이더, 조명, 상호작용 UI를 동시에 수정하면서 회귀 테스트 비용이 커졌다.
- 외부 에셋의 콜라이더, 머티리얼, LOD, URP 호환성 검증이 레벨 배치 이후에 이루어진 경우가 있어 재작업이 발생했다.
- 저장 데이터와 인벤토리 UI 구조가 여러 스크립트에 분산되어 기능 추가 시 영향 범위를 파악하기 어려웠다.
- 역할별 책임은 정해져 있었지만 특정 인원에게 기획, 구현, 디버깅, 발표 준비가 동시에 집중되는 시기가 있었다.

### 트러블슈팅 모음

---

#### 트러블슈팅 1 — 외부 에셋의 Collider 누락

1. **문제 상황 파악**

    마트 환경 및 소품으로 사용할 일부 외부 에셋에 Collider가 없어 플레이어가 오브젝트를 통과하거나 상호작용 판정이 불가능했다.

2. **문제 발생 조건 파악**

    모델을 씬에 배치한 뒤 Mesh Renderer만 존재하고 Collider가 없는 상태에서 플레이어 이동 및 NavMesh를 테스트할 때 발생했다.

3. **결과 검증, 해결**

    에셋별 Collider 유무를 우선 검사하고, 반복 사용되는 오브젝트는 프리팹 루트에서 BoxCollider 또는 MeshCollider를 보정했다. 이동 동선에 직접 영향을 주는 벽과 대형 구조물은 단순화된 Collider를 사용하여 성능과 안정성을 함께 확보했다.

#### 트러블슈팅 2 — 플레이어를 가리는 벽의 투명화 미작동

1. **문제 상황 파악**

    플레이어가 건물이나 벽 뒤에 위치하면 캐릭터가 완전히 가려졌으며, Flat Kit의 Opaque 머티리얼은 알파값을 낮춰도 투명해지지 않았다.

2. **문제 발생 조건 파악**

    카메라와 플레이어 사이에 Opaque 머티리얼을 사용하는 벽 Renderer가 존재할 때 발생했다. LOD Group과 여러 머티리얼 슬롯을 사용하는 벽에서는 단순 교체 방식도 불안정했다.

3. **결과 검증, 해결**

    카메라에서 플레이어 방향으로 `SphereCastNonAlloc`을 실행하여 가림 벽을 감지하고, Shader Graph로 제작한 Transparent Fade 머티리얼로 교체했다. Renderer별 알파값은 `MaterialPropertyBlock`으로 제어해 공유 머티리얼 전체가 변경되는 문제를 방지했다. 감지 해제 시 원본 머티리얼을 복원하여 플레이어 시인성을 확보했다.

#### 트러블슈팅 3 — 손전등 Cone Mesh의 벽 관통

1. **문제 상황 파악**

    ProBuilder Cone과 ConeBeam으로 표현한 손전등 광선이 벽을 무시하고 반대편까지 표시되어 공간 구조가 노출됐다.

2. **문제 발생 조건 파악**

    메시 기반 빔 효과는 물리 Collider와 직접 상호작용하지 않기 때문에 벽 가까이에서 항상 발생했다.

3. **결과 검증, 해결**

    메시 빔 방식을 제거하고 정면용과 발밑 보정용 Spot Light 두 개로 구성했다. URP Shadow를 활용하여 벽에서 광원이 자연스럽게 차단되도록 했으며, 추가 메시 렌더링 없이 공간감과 시인성을 확보했다.

#### 트러블슈팅 4 — 고속 이동 시 얇은 벽과 모서리 관통

1. **문제 상황 파악**

    달리기 또는 대시 시 `Rigidbody.MovePosition()`의 한 프레임 이동 거리가 벽 두께보다 커지면서 얇은 벽이나 모서리를 관통했다.

2. **문제 발생 조건 파악**

    기존 이동 경로 검사는 일부 회피 상태에서만 실행되었고, 상호작용용 Trigger Collider와 실제 몸통 Collider가 분리되지 않아 물리 검사 형상이 불명확했다.

3. **결과 검증, 해결**

    Trigger가 아닌 실제 몸통 `CapsuleCollider`를 별도로 지정하고 모든 이동 상태에서 `CapsuleCast()` 기반 경로 검사를 적용했다. 첫 충돌 후 남은 이동량은 `Vector3.ProjectOnPlane()`으로 벽면 방향에 투영하고, 슬라이딩 경로를 다시 검사하여 모서리 관통을 줄였다.

#### 트러블슈팅 5 — Bloom으로 인한 화면 하얀색 점멸

1. **문제 상황 파악**

    특정 연출이나 오브젝트 활성화 순간 화면 전체가 한 프레임 동안 하얗게 번쩍이는 현상이 발생했다.

2. **문제 발생 조건 파악**

    DOTween으로 Light Intensity 또는 HDR Emission이 순간적으로 증가할 때 Bloom Clamp가 비활성화되어 높은 HDR 값이 제한 없이 가산됐다.

3. **결과 검증, 해결**

    URP Volume의 Bloom Clamp를 활성화하고 씬의 최대 발광 수준에 맞춘 상한값을 적용했다. 원본 광원의 밝기는 유지하면서 Bloom 계산에 사용되는 값만 제한하여 화면 점멸을 제거했다.

#### 트러블슈팅 6 — 창고/인벤토리 데이터 유지와 UI 동기화

1. **문제 상황 파악**

    인게임에서 획득한 아이템을 창고로 이동한 뒤 씬을 다시 진입하면 저장 시점과 UI 갱신 시점에 따라 아이템이 사라지거나 퀵슬롯 표시가 맞지 않는 문제가 있었다.

2. **문제 발생 조건 파악**

    런타임 리스트와 `PlayerSaveData`가 분리되어 있고, 슬롯 이동 후 저장 호출이 누락되거나 UI가 이전 캐시를 사용하면 발생했다.

3. **결과 검증, 해결**

    창고·인벤토리·안전 슬롯·아티팩트·퀵슬롯 데이터를 한 번에 `PlayerSaveData`로 변환하여 저장하고, 패널 활성화 시 저장 데이터를 다시 로드하도록 정리했다. 인벤토리에 존재하지 않는 아이템이 퀵슬롯에 남지 않도록 유효성 검사를 추가했다.

### KPT 회고

*Keep / Problem / Try 형식으로 프로젝트 전반을 회고합니다.*

---

#### 1. Keep — 계속 가져갈 점

- 기능을 만들기 전에 기획 의도와 완료 기준을 문서로 정의하는 습관
- 매일 목표, 완료 작업, 블로커, 트러블슈팅을 기록하는 개발일지 방식
- 문제를 증상으로만 보지 않고 렌더링, 물리, 데이터 흐름 등 원인 계층으로 분해하는 접근
- 외부 에셋을 프로젝트 요구사항에 맞게 검증하고 수정하는 과정

#### 2. Problem — 아쉽거나 문제였던 점

- PD의 담당 범위가 기획, UI, 레벨, 그래픽 디버깅, 발표 준비까지 넓어져 핵심 우선순위가 분산됐다.
- 에셋의 URP, Collider, LOD, Shader 호환성을 초기에 일괄 검증하지 않아 후반 재작업이 발생했다.
- 저장 데이터와 UI 로직이 하나의 큰 클래스에 집중되어 수정 시 회귀 위험이 컸다.
- P0 범위를 넘어선 기능을 추가하면서 일부 문서와 코드의 기준이 달라졌다.
- 기능별 완료 기준은 있었지만 자동화된 테스트나 반복 가능한 회귀 테스트 시나리오가 부족했다.

#### 3. Try — 다음 프로젝트에서 시도할 점

- 첫 주에 외부 에셋 검증 체크리스트를 만들어 Collider, Material, Shader, LOD, Animation, 라이선스를 일괄 확인한다.
- 기획 문서의 항목마다 담당자, 완료 기준, 테스트 방법을 하나의 티켓으로 연결한다.
- 저장 데이터, 도메인 로직, UI 표시를 Model–Presenter–View 수준으로 명확히 분리한다.
- 기능 동결 1주 전부터 신규 기능 추가를 제한하고, 통합 및 회귀 테스트에 집중한다.
- 그래픽 기능은 전후 비교 이미지와 성능 수치를 함께 기록하여 포트폴리오 자료로 활용한다.
- 개인 담당 기능은 Git 커밋, 스크린샷, 테스트 결과를 매주 정리해 최종 회고 시 정량화한다.

### 배운 점 / 성장한 점

*프로젝트를 통해 새롭게 학습한 기술과 개인·팀 차원의 성장을 작성합니다.*

---

#### 1. 새로 학습한 기술

- URP에서 Opaque와 Transparent 렌더링이 처리되는 방식
- Shader Graph와 `MaterialPropertyBlock`을 이용한 Renderer 단위 속성 제어
- Bloom Threshold와 Clamp가 HDR 픽셀에 미치는 영향
- `SphereCastNonAlloc`, `CapsuleCast`, 충돌 법선과 벽면 슬라이딩 계산
- Cinemachine 카메라와 런타임 생성 플레이어의 이벤트 기반 연결
- Spot Light와 Shadow를 활용한 메시 없는 손전등 연출
- Addressables, 저장 데이터와 UI 갱신의 연결 방식

#### 2. 개인적인 성장

처음에는 PD로서 시나리오를 작성하고 에셋과 레벨의 방향성을 정하는 역할에 집중했지만, 프로젝트가 진행되면서 실제 Unity 씬과 코드의 동작을 확인하지 않으면 기획 의도를 완성할 수 없다는 점을 체감했다. 이후에는 문제를 개발자에게 전달하는 데서 끝내지 않고 직접 재현 조건을 만들고, 원인을 분석하고, 수정 방안을 테스트하는 방식으로 참여 범위를 확장했다.

특히 셰이더, 물리 충돌, 저장 데이터처럼 처음에는 익숙하지 않았던 영역을 실제 문제 해결 과정에서 학습했다. 이를 통해 기획·레벨디자인·프로그래밍을 분리된 업무가 아니라 하나의 사용자 경험을 구성하는 연결된 과정으로 바라보게 되었다.

#### 3. 팀 / 협업 측면 인사이트

- 팀이 같은 목표를 공유하려면 역할 설명보다 **완료 기준과 테스트 가능한 결과**가 더 중요하다.
- 문제는 발견 즉시 공유할수록 해결 비용이 작아지며, 숨겨진 블로커는 통합 단계에서 더 큰 재작업으로 돌아온다.
- 기획 문서는 구현을 통제하는 도구이지만, 실제 빌드의 변경사항이 다시 문서에 반영되어야 SSOT로 기능한다.
- 각 역할의 전문성을 존중하면서도, 인터페이스가 맞닿는 지점에서는 공동 검수가 필요하다.
- 개발일지와 트러블슈팅 기록은 단순 과제 제출물이 아니라 팀의 의사결정 근거이자 포트폴리오 자산이 된다.
