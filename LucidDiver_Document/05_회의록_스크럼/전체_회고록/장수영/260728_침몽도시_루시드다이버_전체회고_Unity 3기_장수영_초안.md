## 프로젝트 목표 및 결과

### 1. 초기 목표

초기 기획은 서브컬처 캐릭터 수집·애착 경험과 익스트랙션 장르의 파밍·유실 긴장감을 한 프로젝트 안에 결합하는 것이었습니다. 다만 두 장르는 실패를 받아들이는 방식이 서로 달랐습니다.

- 서브컬처 장르는 캐릭터와의 관계가 계속 유지되어야 애착이 쌓입니다.
- 익스트랙션 장르는 실패 시 획득물을 잃을 가능성이 있어야 선택에 긴장감이 생깁니다.
- 짧은 프로젝트 기간 안에 두 장르의 모든 기능을 구현하는 대신, 결합이 실제 플레이 동기로 작동하는지 검증할 최소 범위를 정의해야 했습니다.

이에 최종 P0의 핵심 질문을 다음과 같이 고정했습니다.

> **“익스트랙션 플레이를 통해 회수한 보상이 서브컬처 캐릭터 애착 보상과 다음 출격 준비로 이어질 수 있는가?”**

초기 완료 기준은 다음 두 루프가 하나의 플레이 사이클 안에서 연결되는 것이었습니다.

1. **캐릭터 애착 루프**  
   기억 파편 획득 → 탈출 성공 → 기억 파편 자동 사용 → 동조율 상승 → 개인 심상 기록 해금 → 귀환 대사 변화
2. **PvE 익스트랙션 루프**  
   마나석(이상한 사탕) / 회복약(변질된 붕대) / 아티팩트(장비 아이템) / 기억 파편 획득 → 탈출 성공 → 창고 저장 → 다음 출격 슬롯 장착 → 다음 세션에서 사용

### 2. 최종 결과물

최종 빌드에서는 다음 흐름을 한 사이클로 경험할 수 있도록 구성했습니다.

```text
로비
→ 출격 준비
→ 침몽도시 세션 진입
→ 이동·조준·공격
→ 적 조우와 아이템 획득
→ 전화부스 탈출 또는 사망에 의한 강제 각성
→ 성공·실패 결과 정산
→ 로비 복귀
→ 심상 기록과 동조율 변화 확인
→ 창고 회수품 확인 및 다음 출격 준비
```

기억 파편은 일반 창고 재화가 아니라 캐릭터 서사를 복구하는 자원으로 분리했습니다. 탈출에 성공하면 동조율과 심상 기록으로 이어지고, 실패하면 해당 세션에서 획득한 파편과 회수품을 잃습니다. 캐릭터 자체는 유지하되 세션의 성과에는 손실을 부여해 두 장르의 핵심 감각을 함께 남겼습니다.

프로젝트 결과는 플레이어블 빌드뿐 아니라 다음 산출물로 정리했습니다.

- 최종 P0 정의서와 시스템·개발 구현 명세
- Unity 플레이어블 빌드 및 전체 시연 영상
- UI 와이어프레임과 실제 런타임 UI
- AnyPortrait 기반 2D 캐릭터 모션과 Live2D 캐릭터 연출
- 58종 SFX·BGM 리소스와 AudioManager 연동 구조
- 프로젝트 공식 PV
- 팀원별 구현 과정과 판단을 직접 조작하며 설명하는 인터랙티브 발표 웹
- Notion 안에서 최종 문서를 탐색할 수 있는 임베드용 문서 뷰어

## 스크럼 회고

### 1. 협업 방식

프로젝트는 7주 일정으로 운영했습니다.

- **06.11~06.19**: 프로젝트 채택, 기획 구체화, P0 정합성 수정
- **06.22**: 최종 기획서 전자서명 및 개발 킥오프
- **06.22~07.03**: P0 코어 구현과 결과 정산 루프 통합
- **07.06~07.17**: QA, 리소스 적용, 회귀 테스트
- **07.20~07.24**: 최종 QA, 발표 웹·대본·예비 영상 제작
- **07.27~07.28**: 최종 리허설과 발표

협업 도구와 기록 방식은 다음과 같았습니다.

- **GitHub**: 문서·웹·미디어 버전 관리, 팀원별 작업 병합
- **Notion**: 일정·업무 보드·공유 문서 확인
- **Markdown SSOT**: P0 범위, 시스템 규칙, 개발 전달 명세 관리
- **개인 개발일지와 데일리 스크럼**: 완료 작업, 블로커, 다음 작업 기록
- **주차별 마일스톤과 DoD**: 기능 구현, 리소스 적용, QA, 발표 준비의 완료 기준 확인
- **코치 피드백 및 팀 회의**: 범위·일정·문서 전달력 조정

### 2. 잘 진행된 점

#### 범위 판단의 기준을 먼저 만들었다

초기에는 세계관, 전투, 캐릭터 성장, 인벤토리, 멀티플레이 등 아이디어가 넓게 퍼져 있었습니다. 최종 P0 정의서를 최상위 기준으로 고정하고 P0.5와 제외 항목을 분리하면서, 새로운 아이디어가 나와도 “좋은 기능인가”보다 “이번 검증 질문에 필요한가”를 먼저 판단할 수 있었습니다.

#### 기능과 리소스 적용 순서를 분리했다

초기 일정은 기능 구현과 애니메이션·UI·에셋 적용이 동시에 진행되는 구조라 병목 위험이 컸습니다. 팀원들과 구현 시간을 다시 확인한 뒤 코어 기능을 먼저 연결하고 리소스를 나중에 적용하는 일정으로 변경했습니다. 이 결정은 기능 오류와 비주얼 오류를 구분해 확인하는 데 도움이 되었습니다.

#### 문서와 실제 화면을 함께 검증했다

UI 와이어프레임, AnyPortrait 모션, Live2D, 오디오 샘플, PV를 먼저 만들어 추상적인 설명을 실제로 보고 들을 수 있게 했습니다. 최종 발표에서도 기획 문서와 런타임 화면을 Before/After 슬라이더로 비교해 기획과 결과가 어떻게 연결되었는지 바로 확인할 수 있게 했습니다.

#### 기록을 남겨 최종 발표의 근거로 전환했다

개인 개발일지와 스크럼 기록을 날짜별로 남겼고, 최종 발표 준비 단계에서는 팀원 5인의 개발일지 156건을 전수 조사해 각자의 대표 작업과 문제 해결 근거를 정리했습니다. 덕분에 발표가 기억에 의존하지 않고 실제 작업 기록을 기반으로 구성될 수 있었습니다.

### 3. 개선이 필요했던 점

#### 초반 역할과 일정의 현실성 검증이 늦었다

기획 초기에는 CP가 일정·기획·리소스 판단까지 넓게 맡으면서 실제 개발 속도와 맞지 않는 일정이 만들어졌습니다. 06.19 팀 회의에서 기능과 리소스 적용을 분리해 조정했지만, 이 검증을 프로젝트 제안 단계에서 더 일찍 했어야 했습니다.

#### 문서가 많아지면서 최신 기준을 찾기 어려운 시기가 있었다

초기 문서와 수정 문서가 함께 남아 있어 같은 기능의 설명이 충돌했습니다. 이후 SSOT, 개발 전달용, 부록, 아카이브로 폴더를 구분했지만, 처음부터 문서 지위와 폐기 규칙을 명확히 했으면 정리 비용을 줄일 수 있었습니다.

## 트러블슈팅 모음

### 1. 넓어진 기획 범위와 비현실적인 일정

1. **문제 상황 파악**
   - 초기 기획에는 캐릭터 수집, 복잡한 인벤토리, 성장, 멀티플레이, 보스, 추가 전투 기믹이 동시에 포함되어 있었습니다.
   - 기능과 애니메이션·UI·에셋을 같은 시기에 완성하려는 일정도 실제 개발 속도와 맞지 않았습니다.
2. **문제 발생 조건 파악**
   - 문서마다 구현 범위가 달랐고, 최종 우선순위를 판단할 단일 기준이 없었습니다.
   - 각 직군의 실제 소요 시간을 확인하기 전에 상위 일정이 먼저 정해졌습니다.
3. **결과 검증, 해결**
   - 최종 P0 정의서를 최상위 SSOT로 지정했습니다.
   - P0, P0.5, 제외 항목을 분리하고 기능 동결 조건을 명시했습니다.
   - 06.19 전체 회의를 통해 `코어 기능 우선 → 리소스 적용 → 회귀 테스트` 순서로 2~7주차 일정을 재편했습니다.
   - 이후 새 아이디어는 P0 핵심 질문과 DoD를 기준으로 판단할 수 있었습니다.

### 2. AnyPortrait와 URP의 알파·그림자 렌더링 문제

1. **문제 상황 파악**
   - AnyPortrait 캐릭터의 투명 영역이 핑크색으로 깨지거나, URP에서 조명을 받지 못하고 그림자 패스에서 제외되는 문제가 발생했습니다.
2. **문제 발생 조건 파악**
   - 기존 셰이더와 URP 렌더 파이프라인의 알파 클리핑·Render Queue·ShadowCaster 처리 기준이 맞지 않았습니다.
   - 투명 스프라이트가 일반적인 불투명 메시와 다른 렌더링 순서를 사용했습니다.
3. **결과 검증, 해결**
   - URP Lit 기반 Shader Graph로 전환하고 알파 클리핑과 Point 필터링을 조정했습니다.
   - 그림자용 레이어와 Renderer Feature 필터, Render Queue, 알파 동기화, Bias를 함께 조정했습니다.
   - 플래시라이트와 씬 조명 아래에서 캐릭터 실루엣과 투명 배경이 정상 표시되는 것을 확인했습니다.

### 3. Canvas 전환 후 Live2D 영상 정지

1. **문제 상황 파악**
   - 출격 준비 화면을 닫았다가 다시 열면 Live2D 캐릭터 영상이 첫 프레임에서 멈췄습니다.
2. **문제 발생 조건 파악**
   - Canvas 비활성화 시 VideoPlayer가 정지되지만, 재활성화 시 재생 상태가 자동으로 복구되지 않았습니다.
3. **결과 검증, 해결**
   - `OnDisable`에서 영상을 정리하고 `OnEnable`에서 재생 준비와 시작을 다시 수행하도록 수명주기를 맞췄습니다.
   - 화면을 반복 전환해도 Live2D 영상이 다시 재생되는 것을 확인했습니다.

### 4. 발표 웹의 첫 진입 미디어와 레이아웃 불안정

1. **문제 상황 파악**
   - 일부 영상은 슬라이드에 처음 진입했을 때 로딩 화면에 멈췄고, 원본 비율이 다른 코드 이미지와 영상은 카드 밖으로 잘렸습니다.
2. **문제 발생 조건 파악**
   - 장면 진입 시 미디어 상태 초기화가 없었고, 서로 다른 비율의 미디어에 동일한 고정 높이를 사용했습니다.
3. **결과 검증, 해결**
   - 장면 진입 시 기본 미디어 상태를 재설정하고 `loadedmetadata`, `loadeddata`, `canplay` 이벤트에 표시 상태를 동기화했습니다.
   - `min-height: 0`, `overflow: hidden`, `object-fit: contain`을 적용해 카드 안에서 원본 비율을 유지했습니다.
   - 첫 진입, 메뉴 이동, 이전·다음 슬라이드 이동을 반복해 미디어가 정상 표시되는지 회귀 테스트했습니다.

### 5. GitHub Pages 404와 Notion 외부 이동 문제

1. **문제 상황 파악**
   - Notion 임베드용 페이지는 GitHub Pages에서 404가 발생했고, 파일을 클릭하면 Notion을 벗어나 GitHub 새 탭으로 이동했습니다.
2. **문제 발생 조건 파악**
   - 진입 파일이 대문자 `Index.html`이었고, GitHub Pages는 대소문자를 구분해 소문자 `index.html`을 찾았습니다.
   - 파일 목록이 GitHub `blob` 링크로만 구성되어 있었습니다.
3. **결과 검증, 해결**
   - 진입 파일을 소문자 `index.html`로 변경했습니다.
   - GitHub Trees API와 Raw URL을 이용해 `LucidDiver_Document` 하위 문서만 탐색하도록 범위를 제한했습니다.
   - Markdown·코드·이미지·영상·오디오·PDF를 같은 임베드 안에서 보여주는 인라인 프리뷰를 구현했습니다.
   - 디렉터리 URL 진입, 파일 검색, 폴더 이동, 미디어 프리뷰가 정상 동작하는 것을 확인했습니다.

## 배운 점 / 성장한 점

### 1. 새로 학습한 기술

- **AnyPortrait**의 메시·Bone 리깅, 가중치, 방향별 애니메이션 제작
- **Live2D Cubism**의 파츠 구성과 Unity UI 영상 연동
- **URP Shader Graph**의 Lit, 알파 클리핑, Render Queue, ShadowCaster 처리
- **FL Studio**를 활용한 게임 SFX/BGM의 트리밍, EQ, 음량 정리와 후가공
- **HTML/CSS/JavaScript** 기반 인터랙티브 발표와 미디어 수명주기 제어
- **GitHub Pages**의 정적 배포 규칙과 파일명 대소문자 문제
- **GitHub API/Raw URL**을 활용한 Notion 임베드형 문서 탐색기
- **Markdown SSOT**와 상대경로·버전 규칙을 이용한 대규모 문서 관리

### 2. 개인적인 성장

가장 크게 성장한 부분은 기획을 많이 쓰는 것과 팀이 구현할 수 있게 만드는 것이 다르다는 점을 체감한 것입니다. 아이디어를 확장하는 능력만으로는 프로젝트가 완성되지 않았습니다. 무엇을 이번 빌드에 넣고, 무엇을 미루며, 어떤 결과를 성공으로 볼지 선을 긋는 판단이 필요했습니다.

또한 제가 가진 미술·음악·UI의 보조 역량은 다른 직군의 일을 대신하기 위한 것이 아니라, 추상적인 기획을 빠르게 검증하는 수단으로 사용할 때 가장 효과적이었습니다. UI 목업으로 화면 흐름을 보여주고, AnyPortrait와 Live2D로 캐릭터 표현 가능성을 확인하며, 사운드 샘플과 PV로 게임의 분위기를 공유하자 문서만으로 논의할 때보다 피드백이 구체적으로 바뀌었습니다.

마지막으로 최종 발표 웹과 대본을 제작하면서, 좋은 발표는 결과를 나열하는 것이 아니라 문제·판단·구현·검증을 청중이 따라올 수 있게 구성하는 일임을 배웠습니다.

### 3. 팀 / 협업 측면 인사이트

- 팀이 빠르게 움직이려면 문서의 양보다 최종 판단 기준이 명확해야 합니다.
- 담당자의 전문성을 존중하면서도 서로의 결과가 연결되는 지점을 공통 언어로 설명해야 합니다.
- 말로 합의한 내용은 구현 단계에서 다르게 해석될 수 있으므로 화면, 변수, 상태 변화, 완료 조건으로 남겨야 합니다.
- 작은 프로토타입 하나가 긴 회의보다 빠르게 오해를 발견하게 해줄 수 있습니다.
- 최종 발표 자료는 프로젝트 마지막에 새로 만드는 것이 아니라, 개발 과정의 기록과 검증 자료를 편집해 만드는 것이 가장 안정적입니다.
